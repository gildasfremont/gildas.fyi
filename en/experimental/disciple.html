Describing the work to be done instead of building an agent

An architect, an orchestrator and agents, built and put to the test in ten days

March 22–31, 2026 · prototype · Python, FastAPI, SQLite · built with Claude Code · full write-up (Markdown)

Agent platforms usually start by having you build an agent, with its prompt, its tools and its permissions. Disciple starts from the work itself: you describe it, and the rest organizes itself on three levels.

Held to the methodExecution agents follow a method and remember, from one run to the next, their strengths and weaknesses.
Held to the resultThe orchestrator judges each deliverable against the goal, and sends back whatever doesn't hold up.

Every run has a maximum budget, in tokens and in time.

Ten test sessions

The prototype was put through test sessions played by personas: five job profiles and an acceptance tester. From one session to the next, it became more reliable.

  1. sessions 1 and 2Run through the command line, the architect had no access to native tools and asked questions instead of acting. Tool calls, simulated as JSON in the text, gave it back control: each persona gets its plan in a single exchange.
  2. session 3On large plans, a sliding window over the history takes the batches from 3/5 and 3/6 successful tasks to 6/6, 7/7 and 6/6.
  3. session 4Five runs for $1.53 in total.
  4. session 7First complete run, in about three minutes.
  5. session 956/56 acceptance checks.
  6. session 10207/216 across thirteen scenarios, with three-layer evaluations that grade the result rather than the path taken.

In ten days and 84 commits, the prototype learned to run the exchange with the architect, produce a plan, launch the tasks, present the results and keep a memory, and it got continuous integration. Its backlog holds 47 ideas, about thirty of them implemented in a single day, March 24.
